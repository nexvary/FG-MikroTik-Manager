# DNS family/privacy protection — Android 0.16.0

Advanced setup → Block adult content, ads & trackers. Existing authenticated RouterOS transport and business router permission/audit wrappers are reused. Two profiles use public AdGuard DNS: Family 94.140.14.15/94.140.15.16 (adult domains, ads, trackers, Safe Search where supported); Ads/Trackers 94.140.14.14/94.140.15.15. Provider documentation: https://adguard-dns.io/en/public-dns.html and https://adguard-dns.io/kb/general/dns-filtering/ . RouterOS DNS and DHCP references: https://manual.mikrotik.com/docs/network-management/dns/ and https://manual.mikrotik.com/docs/network-management/dhcp/server/ .

Select existing private or carrier-grade NAT DHCP IPv4 networks, review the plan, then Back up & apply. No private credentials are sent to the DNS provider. The provider receives conventional DNS queries; this feature does not claim encrypted DNS transport. Router DNS also changes, including resolver users/HotSpot, and existing DoH and enabled DHCP/PPPoE peer DNS are disabled with original values retained. Only selected DHCP network DNS/dns-none fields change. No firewall, IP addressing, route, public DNS enablement, TLS certificate or password changes. Unfiltered dynamic upstream DNS remaining after apply causes failure/recovery rather than claiming filtering.

Only canonical private/client networks are eligible; no creation of new DHCP networks. Custom network DHCP options require manual review. Maximum 32 selected networks and 128 setting groups per operation. Unknown reads/permissions, missing Ethernet MAC identity, stale plans and failed backups/journal persistence prevent configuration writes. Plans are revalidated immediately before execution, each setting is checked before and after writes. RouterOS has no atomic compare-and-set for these commands; a tiny race with another administrator remains, so do not edit the same DNS settings concurrently.

An existing encrypted router backup is verified and its password protected using the existing Android Keystore vault. A durable encrypted original/expected setting journal precedes the first mutation, so lost replies can be recovered. Automatic failure recovery restores only values still matching original/applied values. Uncertain/conflicting outcomes retain the journal for Review; no success is inferred from a request being sent. Stop filtering & restore verifies router MAC fingerprint and target network ID/address, preserves unrelated settings, and refuses later third-party edits. The fingerprint identifies an observed Ethernet MAC set, not cryptographic device attestation. Backup restoration is still available in the existing Recovery section. Journal and backup password are device-local and not cloud synchronized. Do not clear app storage if recovery is pending.

Readback confirms configuration, not censorship effectiveness on clients. Existing client leases/cache require reconnect/renewal and actual testing. Local DNS names may be affected. Filtering depends on provider lists/reachability and traffic using those resolvers; VPN/Private DNS/DoH/DoT/manual DNS, separate IPv6 DNS, custom PPP DNS, per-lease/server/RADIUS DHCP overrides and local static/forward DNS records can bypass it. No firewall-based enforcement or HTTPS interception is claimed. First-party video/social ads, including many YouTube ads, cannot be removed selectively by DNS. No guaranteed 100% blocking, browsing counters, per-subscriber enforcement or DNS logs fabricated.

Automated verification covers filtered resolver profiles, selected subnet scope, preserved resolver exposure/firewall, original DoH/peer DNS restoration, stale plan/read/backup/journal failure, lost acknowledgement, later edit/replaced-router conflict, ignored writes/dynamic fallback, idempotence, subnet validation and Arabic/English disconnected-screen scrolling/Back. Transport fixtures are tests only; none are product data. Physical MikroTik/client acceptance remains pending.
